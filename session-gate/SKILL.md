# session-gate

Сначала цифры, потом вердикт. Отвечай не «как ощущается», а по метрикам и весам.
Ты — самая предвзятая сторона этого спора: не видишь свой token-метр, видишь только
projection после компакции и заинтересован продолжать (sunk cost). Поэтому вердикт
выдаётся только на двух и более подтверждающих сигналах.

## Шаг 1 — измерение

```bash
node "<этот-скилл>/scripts/ctx.mjs"          # компактный отчёт
node "<этот-скилл>/scripts/ctx.mjs" --json   # машинный вид
```

Скрипт берёт `$PI_SESSION_FILE` (или самый свежий файл сессии текущего cwd).
Окно модели неизвестно (кастомный провайдер, своя модель) → `--window N` или `SESSION_GATE_CONTEXT_WINDOW=N`.

Что читаем из вывода: `stage` (ok / warn / hot), `контекст` (токены и % от окна), `ходы`
(user / assistant / tool), `шум` (накопленный tool-вывод и его кратность текущему контексту),
`сжатия` (compactions / branch / model_change), `время`, `запросы пользователя`, `файлы`.

`cost n/a` — норма для кастомных провайдеров: цену как сигнал не используем. Окно 1M у
`deepseek-flash` означает, что токены почти никогда не решают — решает смысл сессии.

## Шаг 2 — сигналы

Считай только то, что подтверждено выводом скрипта или явно видно в диалоге. Нет признака — 0, не выдумывать.

| # | Сигнал | Как проверить | Вес |
| --- | --- | --- | --- |
| 1 | Дрейф задачи | текущий запрос не про то, с чего начали (запрос №1 vs последний) | +3 |
| 2 | Тупики | те же провалы ≥2, откаты правок, «не вижу / забыл / почему не применилось» | +3 |
| 3 | Контекст | `stage=hot` → +2, `stage=warn` → +1 | +1…+2 |
| 4 | Шум | `шум ×≥1` текущего контекста или `tool ≥150` вызовов | +2 |
| 5 | Нужны точные детали начала | следующий шаг требует номеров строк, текстов ошибок, дословных решений из начала | +2 |
| 6 | Длинная серия без пользователя | `assistant ≥100` на `user=1…3` | +2 |
| 7 | Смена режима | работа → ревью / PR / релиз / новая заметка | +1 |
| 8 | Незакрытый артефакт | правка в середине, тест красный, линтер не прогнан | −2 |
| 9 | Дешёвый переприминг | в новой сессии нечего перечитывать (≤2 файла) | −1 |

## Шаг 3 — вердикт

Сумма весов:

| Сумма | Вердикт | Что значит |
| --- | --- | --- |
| ≥4 | **ПОРА** | новая сессия + пакет передачи |
| 2–3 | **СЖАТЬ** | один поток работы, дрейфа нет → `/compact <инструкция>` |
| 2–3 при новой ветке вопроса | **ФОРК** | `/fork` от нужного user-сообщения, текущая линия сохраняется |
| ≤1 | **МОЖНО** | продолжать, ничего не менять |

Жёсткие исключения (перекрывают сумму):

- `stage=hot` → минимум СЖАТЬ, даже при сумме 0.
- `compactions ≥2` и сменилась задача → ПОРА.
- Новый запрос про другие файлы/темы, не связанные с текущими → ПОРА, независимо от суммы.

По умолчанию — МОЖНО. Ротация стоит дорого: она оправдана только если пакет передачи
получается без потерь.

## Шаг 4 — формат ответа

```
ВЕРДИКТ: ПОРА | СЖАТЬ | ФОРК | МОЖНО
цифры: ctx 65,373 (6.6%) · ходы 3/144 · шум ×0.7 · сжатия 1 · 29m
почему: 1) …  2) …  (пункты с цифрами, не больше трёх)
дальше: конкретная команда пользователю
```

Пакет передачи — обязателен для ПОРА и ФОРК:

```markdown
## Пакет в новую сессию
Цель: …
Сделано: …
Решения: … (с причинами, чтобы не пересматривать)
Следующий шаг: …
Файлы: …
Грабли: … (что уже пробовали и почему не сработало)
```

- СЖАТЬ → выдай готовую строку: `/compact сохрани цель, принятые решения и следующий шаг; …`
- МОЖНО → один абзац: что продолжать и на что смотреть, если контекст начнёт мешать.

## Запреты

- Не запускай `/new`, `/compact`, `/fork` за пользователя — это его команды в TUI. Дай строку.
- Не пересказывай историю сессии целиком: только вердикт, цифры, пакет передачи.
- Не выдавай ПОРА «на всякий случай» при сумме ≤1 и не смягчай ПОРА до «наверное».
- Не подменяй измерение самоощущением: если цифры расходятся с ощущением — правы цифры.
- Не считай токены единственным аргументом: при окне 1M это почти всегда не причина.
